## 0) Context and Why This Path
The target exposed an n8n instance. n8n is very powerful: if you can control workflows/nodes, you can often execute logic that reaches internal resources.

So the plan was:
1. Find unauthenticated exposures
2. Get valid n8n admin access
3. Abuse workflow execution
4. Pivot from container context to host context
5. Read `/root/proof.txt`

## 5) Container-to-Host Pivot via Docker Socket

Inside workflow code execution, we found `/run/docker.sock` mounted.

Why this is huge:
- Docker socket = Docker API control.
- Docker API control often means host compromise if privileged containers can be created.

We then created a helper container with:
- `Privileged: true`
- host bind mount `/:/host`
- root user inside helper container

Then read:
- `/host/root/proof.txt`

## 7) Why It Worked (Root Cause)

Primary weaknesses:
1. Unauthenticated debug endpoint leaked credentials
2. n8n owner account could modify workflows directly
3. Docker socket was exposed to the app execution context
4. Privileged helper container creation was allowed

This is a full chain from **info leak -> auth compromise -> workflow RCE primitive -> host compromise**.

---

## 8) What to Fix (Defense)
1. Remove/lock debug endpoints (`/webhook/health` etc.)
2. Put n8n management/API behind strict auth/network ACL
3. Never mount Docker socket into app containers
4. Enforce least privilege and deny privileged container creation
5. Separate app runtime from host-sensitive control planes
